# План реализации нейро-стенографиста для Redmi Note 11S

Дата: 6 ноября 2026 года. Статус: утверждённый пользователем план реализации. Этапы ниже описывают предстоящую работу, а не уже реализованные функции.

## 1. Результат и принятые решения

Сделать Android-приложение, которое после установки APK без интернета импортирует разговор, распознаёт речь, разделяет участников, показывает реплики с временными метками и экспортирует JSON. Обязательная локальная LLM формирует **отдельное резюме**, не изменяя расшифровку и экспорт для оценки.

Основание — требования, схема JSON, процедура проверки и критерии из [предоставленного задания](source/Хахатон%20Ноябрь%202026.pdf).

Приняты следующие ограничения первой версии:

- Основное устройство — Redmi Note 11S с Helio G96; планируем под конфигурацию с 6 ГБ RAM. У модели также есть вариант с 8 ГБ. Фактические RAM, Android и ABI записать перед первым тестом. [Характеристики Xiaomi](https://www.mi.com/in/product/redmi-note-11s/specs/).
- Все модели включаются в APK. При первом запуске копируются в приватный каталог приложения с проверкой целостности.
- Вычисления выполняются на CPU, модели загружаются последовательно.
- Основной язык — русский. Начальные тесты: 2–3 участника, записи 1–5 минут; это тестовый набор, а не гарантированные пределы приложения.
- Обязательный импорт: WAV PCM и M4A/AAC. Остальные форматы получают явное сообщение о неподдерживаемом формате.
- Запись с микрофона, редактирование, облачная синхронизация и разделение одновременно звучащих голосов остаются за пределами MVP.

Текущая база уже содержит Expo-приложение, выбор файла, тип JSON и основу Kotlin-модуля. Нативную сборку и инференс ещё необходимо проверить.

## 2. Архитектура, модели и контракты

### Стек

| Подсистема | Решение |
|---|---|
| Интерфейс | Существующие React Native, TypeScript, Expo SDK 58 |
| ASR и диаризация | sherpa-onnx **2.0.1**, Kotlin API и нативные библиотеки одной версии |
| Русское ASR | GigaAM v2 CTC INT8: `sherpa-onnx-nemo-ctc-giga-am-v2-russian-2025-04-19` |
| Диаризация | Pyannote segmentation 3.0 INT8 + `3dspeaker_speech_eres2net_base_sv_zh-cn_3dspeaker_16k.onnx` |
| Локальная LLM | `llama.rn` **0.12.9** + Qwen2.5-0.5B-Instruct, GGUF `Q4_K_M` |
| Аудиоподготовка | Kotlin, MediaExtractor/MediaCodec для M4A, преобразование в mono 16 kHz |
| Хранение | Файлы JSON в приватном каталоге приложения |
| Экспорт | `expo-file-system` и `expo-sharing` |

Выбраны опубликованные стабильные релизы [sherpa](https://github.com/k2-fsa/sherpa-onnx/releases/tag/v2.0.1) и [llama.rn](https://github.com/mybigday/llama.rn/releases/tag/v0.12.9). Модели доступны в готовых форматах: [GigaAM](https://k2-fsa.github.io/sherpa/onnx/pretrained_models/offline-ctc/nemo/russian.html), [диаризация](https://k2-fsa.github.io/sherpa/onnx/speaker-diarization/models.html), [Qwen GGUF](https://huggingface.co/Qwen/Qwen2.5-0.5B-Instruct-GGUF). Их совместная работа на выбранном телефоне пока не подтверждена.

### Последовательность обработки

1. Скопировать выбранный файл в каталог приложения и определить его фактический формат.
2. Декодировать звук, свести каналы и привести к mono 16 kHz. Сохранить длительность исходной записи.
3. Выполнить диаризацию всей записи с автоматическим количеством участников.
4. Сохранить интервалы и освободить модели диаризации.
5. Загрузить GigaAM, распознать интервалы последовательно, освободить ASR.
6. Сохранить и показать расшифровку; экспорт уже доступен.
7. Загрузить Qwen, сформировать отдельное резюме, сохранить его и освободить LLM.

Speaker ID назначаются по первому появлению голоса и сохраняются внутри записи. Метки относятся к исходному файлу. Разрывы длинной реплики для ASR не создают новых участников.

### Интерфейс нативного модуля

В существующем `audio-engine` добавить:

- `prepareModels()` — подготовка локальных файлов моделей.
- `transcribe(fileUri)` — асинхронная обработка аудио с возвратом структурированной расшифровки.
- События стадии и прогресса: подготовка, диаризация, распознавание.
- `cancel()` — кооперативная отмена с освобождением ресурсов; допускается ожидание завершения текущего блока инференса.

Оркестратор на TypeScript запускает LLM только после завершения и освобождения sherpa. Одновременно разрешена одна задача.

Внешний JSON строго соответствует заданию:

```ts
type TranscriptExport = {
  transcript: {
    speaker_id: string;
    start_ms: number; // целое число
    end_ms: number;   // целое число
    text: string;
  }[];
};
```

Имена участников, резюме, сведения о моделях и замеры хранятся отдельно. В сдаваемый JSON дополнительные поля не добавляются.

### Параметры первой конфигурации

- sherpa: CPU, два потока; автоматическая кластеризация, начальный порог `0.5`.
- Qwen: CPU, два потока, контекст 2048 токена, температура `0`, ответ до 160 токенов.
- Резюме: до трёх пунктов на русском, только по содержимому разговора. Текст расшифровки передаётся как данные, а не инструкции.
- Длинный разговор делится по репликам на блоки, помещающиеся в контекст; промежуточные итоги сводятся тем же способом.

Ошибка LLM сохраняет доступ к расшифровке и позволяет повторить резюме. При этом обязательная LLM-функция не считается готовой, пока реальный запуск не пройдёт на телефоне.

## 3. Этапы работы и распределение команды

### Распределение

| Участник | Основная ответственность |
|---|---|
| 1 | Android-сборка, доставка моделей, sherpa, диаризация |
| 2 | Декодирование аудио, GigaAM, сборка реплик и временных меток |
| 3 | React Native UI, сохранение, экспорт, подключение llama.rn |
| 4 | Тестовые записи, эталоны, замеры, интеграционные проверки и материалы сдачи |

Участник 1 отвечает за изменения общей нативной конфигурации. Остальные согласуют с ним Gradle/JNI-зависимости.

### План на 21 час

`T+0` — подтверждённое начало рабочего окна. Завершение — **7 ноября 2026 года, 21:00 МСК**. Расписание не предполагает, что каждый участник работает все 21 час подряд.

| Интервал | Работа | Результат |
|---|---|---|
| **T+0–2** | Сборка APK на Redmi; отдельный запуск диаризации, ASR и Qwen | Подтверждена загрузка и работа трёх ML-компонентов |
| **T+2–5** | WAV → диаризация → ASR → экран → JSON | Первый полный сценарий на новой записи |
| **T+5–9** | Отдых со сдвигом; завершение независимых задач | Сохранённая рабочая сборка, восстановление команды |
| **T+9–13** | M4A, отдельное резюме, сохранение, отмена и ошибки | Закрыты обязательные функции |
| **T+13–16** | Проверка speaker ID, коротких реплик, границ и скорости | Улучшение качества на собственных эталонах |
| **T+16–18** | Регрессия, повторные обработки, авиарежим, память | Зафиксированы фактические результаты |
| **T+18–20** | Финальный APK, инструкция, видео, отчёт | Полный комплект сдачи |
| **T+20–21** | Проверка установки и отправка | Резерв перед стопкодингом |

Если подготовка до официального окна разрешена, первые технические проверки выполнить заранее.

**Контрольные точки:**

- Через два часа должны работать реальные модели на Redmi. При проблемах сборки или памяти команда приостанавливает дополнительные функции и исправляет этот блокер.
- Через пять часов должна работать обработка новой записи с экспортом.
- К T+13 обязательные возможности должны быть объединены.
- После T+16 — исправления и проверки; новые функции не добавляются.
- В первую очередь сокращаются оформление, переименование и дополнительные удобства. Обязательные LLM, ASR, диаризация, метки и экспорт сохраняются.

## 4. Проверки и критерии готовности

### Автоматические проверки

- TypeScript и ESLint.
- Экспорт: точные названия полей, строковые ID, целые миллисекунды, корректная структура пустого результата.
- Метки: `0 ≤ start_ms < end_ms ≤ duration_ms`; сохранение смещения после нарезки.
- Аудиоподготовка: mono/stereo WAV, WAV с дополнительными RIFF-чанками, M4A/AAC с проверкой длительности после преобразования.
- Ошибки: повреждённый файл, неподдерживаемый кодек, отсутствующая модель.

### Проверки на Redmi Note 11S

Подготовить собственные записи с ручным эталоном: один участник, два участника с возвращением говорящего, три участника, короткие ответы, тишина, шум и перебивание.

Для каждой записи сохранить:

- исходное аудио, эталон и фактический JSON;
- WER, ошибки принадлежности реплик и временных границ;
- время подготовки, диаризации, ASR, LLM и полное время;
- RTF полного сценария, пиковую память и параметры устройства.

Сравнивать speaker ID после сопоставления голосов: номера кластеров сами по себе произвольны. Для собственных WER-замеров применять одинаковую нормализацию эталона и результата: нижний регистр, `ё → е`, удаление пунктуации, схлопывание пробелов; числа не преобразовывать.

### Условия приёмки MVP

- APK устанавливается на Redmi и содержит все необходимые модели.
- После установки и подготовки файлов новая запись проходит обработку в авиарежиме без Metro и компьютера.
- Работают WAV и M4A/AAC, просмотр, сохранение и JSON-экспорт.
- Резюме действительно создаётся локальной LLM; расшифровка и экспорт при этом не изменяются.
- Три последовательные обработки завершаются без падения и накопления нативных ресурсов.
- Тишина не порождает искусственные реплики.
- Ошибка или отмена не оставляет приложение в бесконечном состоянии обработки.

Численные пороги WER и RTF не объявляются гарантированными: PDF их не задаёт, а скорость на телефоне ещё не измерена.

## 5. Поставка, отчёт и допущения

- Собрать release APK для `arm64-v8a` со встроенными моделями и JS. Подготовку Android выполнять через Expo-конфигурацию и воспроизводимые плагины.
- Зафиксировать версии библиотек, источники, лицензии и SHA-256 моделей. Большие веса не добавлять в обычный Git.
- Разместить APK и видео в GitHub Release этого репозитория; в README дать прямые ссылки. Документацию и результаты тестов хранить в Git.
- Подготовить семь материалов из задания: APK, исходники, инструкцию, архитектуру и модели, ограничения, собственные тесты, видео.
- Сохранить существующую папку приложения `app/`; добавить отчётные материалы согласно структуре шаблона организаторов без переноса работающего проекта во время хакатона.
- В ограничениях честно описать одновременную речь, ошибки коротких реплик, возможности маленькой LLM и фактическую скорость Redmi.

Допущения: используется обычный Redmi Note 11S, не версия 5G; базовый бюджет памяти — 6 ГБ; отдельное резюме считается функцией обязательной LLM; доставка крупных артефактов через GitHub Release допустима. Эти трактовки требований фиксируются в документации и выносятся на Q&A с организаторами.
