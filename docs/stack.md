# Технологический стек и архитектура

Обновлено: 6 ноября 2026 года. Статус: выбранный маршрут; интеграция и производительность пока не проверены.

> Уточнение по [официальному заданию](brief-analysis.md): локальная LLM обязательна. Её модель/runtime пока не выбраны; текущая связка ASR + диаризация без этого этапа не закрывает задание.

## 1. Основное решение

**React Native + TypeScript + Expo development build → локальный Expo Module на Kotlin → sherpa-onnx.**

React Native отвечает за интерфейс и пользовательский сценарий. Kotlin выполняет подготовку аудио, вызовы ML и сборку расшифровки. Все вычисления и файлы результата остаются на устройстве.

Один нативный ML-движок уменьшает количество интеграций. CPython/Chaquopy в базовую архитектуру не входят. Для интерфейса достаточно стандартных компонентов React Native и состояния React.

## 2. Компоненты

| Задача | Технология | Примечание |
| --- | --- | --- |
| UI | React Native, TypeScript | Выбор записи, прогресс, реплики |
| Инструменты | Expo development build | Своя Android-сборка с нативным модулем |
| Связь с Kotlin | Expo Modules API, локальный audio-engine | Асинхронный вызов обработки и события |
| Импорт | expo-document-picker | Копирование выбранного файла в локальный каталог |
| Файлы | expo-file-system | JSON, TXT, пути к данным |
| Экспорт | expo-sharing | Передача экспортированного файла |
| Нативный pipeline | Kotlin, Coroutines | ML вне главного потока |
| ASR и диаризация | sherpa-onnx | Согласованные Kotlin/JNI и нативные библиотеки |
| Локальная LLM | Выбрать и проверить на этапе A | Обязательная часть задания; роль уточнить у организаторов |
| Воспроизведение | Выбрать после MVP | Не является блокером первого диалога |

Expo Go не подходит для произвольного собственного ML-модуля. Используем development build при разработке и release APK со встроенным JavaScript для демо.

## 3. Модели

### Распознавание русского

Первый кандидат: **GigaAM v2 CTC INT8** в готовом формате sherpa-onnx:

`sherpa-onnx-nemo-ctc-giga-am-v2-russian-2025-04-19`

Нужны `model.int8.onnx` и `tokens.txt`. В документации указан файл модели около 226 МБ. Размер на диске не равен расходу RAM. Проверить точность, скорость и доступность меток в выбранной версии Kotlin API.

Пунктуация и оформление чисел не считаются гарантированным результатом этой CTC-модели; при необходимости это отдельное улучшение.

### Диаризация

Использовать готовую совместимую комбинацию из официального Android-примера sherpa: **Pyannote segmentation 3.0 + модель speaker embeddings**. Точный файл embedding-модели закрепить после первого успешного запуска.

Сегментация определяет интервалы, embeddings описывают голоса, кластеризация объединяет интервалы одного участника. Основной режим — автоматическое число кластеров. Настройку известного числа участников можно добавить отдельно.

Применение ONNX-модели сегментации через sherpa не требует переносить Python-пакет pyannote.audio в приложение.

### Выбор и поставка

- Начать с CPU и официальных готовых моделей.
- Загружать модели из локального каталога приложения; способ включения в поставку проверить на этапе A.
- Для финальной офлайн-проверки все модели должны быть доступны заранее.
- После успешной интеграции закрепить версии зависимостей, файлов моделей, источники, лицензии и SHA-256.
- Большие веса и APK не хранить в обычном Git. Способ доставки моделей описать в инструкции сборки.

## 4. Pipeline первой версии

1. Выбрать WAV и скопировать его в каталог приложения.
2. Проверить заголовок, PCM 16-bit, mono и 16 kHz. Неподдерживаемый формат явно отклонить.
3. Передать локальный путь в audio-engine.
4. Прочитать аудио и выполнить диаризацию всей записи.
5. Получить интервалы начала/конца и speakerId.
6. Распознать каждый интервал отдельно.
7. Собрать и отсортировать реплики по исходному времени.
8. Выполнить согласованную функцию локальной LLM, сохранив исходный результат ASR для сравнения.
9. Сохранить внутренний результат, показать диалог, экспортировать JSON по заданию и дополнительный TXT. Порядок и роль LLM требуют подтверждения и замера производительности.

Для M4A на следующем этапе нужны MediaExtractor/MediaCodec, сведение каналов и явный ресэмплинг до требуемой частоты. Изменение значения sampleRate без преобразования сэмплов недопустимо.

Важные ограничения:

- Пауза не является доказательством смены говорящего.
- speakerId должен быть устойчивым в пределах всей записи.
- Нельзя объединять реплики одного человека через промежуточную реплику другого.
- Временные метки должны относиться к исходному файлу, а не к началу вырезанного фрагмента.
- Короткие фрагменты теряют контекст ASR. Распознавание длинных фрагментов с распределением слов по говорящим — последующее улучшение.
- При нехватке памяти выгружать модели диаризации перед запуском ASR; ресурсы освобождать явно.

## 5. Контракт данных

Проектируемый интерфейс, а не готовый API sherpa:

```ts
export type Utterance = {
  id: string;
  speakerId: number;
  startMs: number;
  endMs: number;
  text: string;
};

export type Transcript = {
  schemaVersion: 1;
  id: string;
  sourceName: string;
  durationMs: number;
  createdAt: string; // ISO 8601
  speakers: { id: number; displayName: string }[];
  utterances: Utterance[];
};

export type ProcessingProgress = {
  stage: 'preparing' | 'diarizing' | 'transcribing' | 'saving';
  completed?: number;
  total?: number;
};

// Планируемый вызов после реализации локального модуля:
// const transcript: Transcript = await AudioEngine.process(localFilePath);
```

Между JS и Kotlin передаются локальный путь, небольшие события прогресса и результат. Большие массивы PCM остаются в нативной части. В первой версии разрешена одна задача обработки одновременно. Для диаризации можно показывать название стадии; для ASR — количество обработанных интервалов.

Инварианты: startMs ≥ 0, endMs > startMs, endMs ≤ durationMs; каждый speakerId есть в speakers. Пересекающиеся интервалы могут отражать одновременную речь и требуют отдельной проверки качества.

### Внешний JSON по заданию

Внутренние типы выше не являются схемой сдаваемого файла. Экспорт должен возвращать:

```ts
export type TranscriptExport = {
  transcript: {
    speaker_id: string;
    start_ms: number; // integer milliseconds
    end_ms: number;   // integer milliseconds
    text: string;
  }[];
};
```

Преобразователь формирует стабильные строковые ID вида `speaker_1` и целые миллисекунды. Нельзя экспортировать внутренний `Transcript` вместо этой схемы. Основание: стр. 15 PDF.

## 6. Создание проекта

Понадобятся Node.js/npm, Git, JDK и Android SDK. Совместимые версии Node/JDK/Gradle выбрать по фактически созданной версии Expo и закрепить после проверки. Каркас уже создан в `app/`; для существующей копии используйте `npm ci` и команды из `app/README.md`. Команды ниже оставлены как справка по первоначальному созданию; повторять их поверх текущего проекта не нужно.

Выполнять из корня репозитория. Вложенная папка app отделяет приложение от документации:

```powershell
npx create-expo-app@latest app --template blank-typescript
cd app
npx expo install expo-dev-client expo-document-picker expo-file-system expo-sharing
npx create-expo-module@latest --local
```

В диалоге создания модуля указать имя `audio-engine`. Затем подключить Android-устройство с USB debugging и выполнить:

```powershell
npx expo run:android
```

Команда создаёт/собирает нативный Android-проект. Изменения Kotlin или нативных зависимостей требуют пересборки. Первую успешную конфигурацию сохранить вместе с lockfile. Код нативной интеграции хранить в локальном модуле; изменения генерируемых файлов Android должны воспроизводиться через конфигурацию проекта.

Важный предел готовых обёрток: в проверенной таблице react-native-sherpa-onnx распознавание поддерживается, а диаризация ещё отмечена как не реализованная. Поэтому основной маршрут — собственный небольшой Expo Module поверх Android API sherpa. whisper.rn остаётся альтернативой ASR после отдельного теста; он не заменяет диаризацию и добавляет вторую интеграцию.
