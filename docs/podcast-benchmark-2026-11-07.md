# Проверка десяти аудиофайлов — 7 ноября 2026

Текущий APK ещё нельзя считать точным стенографистом для подкастов. На размеченных файлах обнаружено чрезмерное разделение одного голоса на разные speaker ID; локальная LLM также может искажать факты. Успешное завершение обработки и правильная структура JSON не подтверждают качество текста.

## Что запускалось

Release v1.0.0-hackathon.1, SHA-256 `1652b8f8d0d1d201079d07341b615586d2ebfd2d49447141adc853651870766d`. Реальное установленное приложение, не Python-замена ASR: импорт через Android DocumentsUI → диаризация → GigaAM → Qwen → просмотр JSON. Android-эмулятор Medium_Phone_API_37.0, x86_64, настроено 4096 МБ RAM. На Redmi/ARM эти результаты не переносим; отдельная проверка авиарежима описана в [smoke-отчёте](android-smoke-2026-11-07.md).

10 подготовленных файлов суммарно около 48 минут 40 секунд: короткий запрос, тишина, четыре синтетических разговора с 1–3 участниками, двухминутный фрагмент и три полных русских подкаста. По метаданным ru-book все четыре смеси имеют SNR 25 dB; доля двойных перекрытий среди речевых интервалов — 0 / 12,4 / 2,5 / 4,5%. Фрагмент t07 взят из t08; файлы не являются десятью независимыми источниками. Отдельного естественного многочасового интервью, телефонного кодека, английского и сильно повреждённого звука в этой выборке нет.

## Результаты

Время — до получения JSON, с накладными расходами опроса интерфейса. На t03–t08 резюме в момент чтения JSON ещё создавалось: это не полное время сценария с LLM. Для t01/t02/t09/t10 замер выполнен после завершения обработки. Разные границы замера отражены полем completion_scope в JSON; эти времена нельзя напрямую использовать для сравнения скорости LLM. ## Как интерпретировать метрики

WER измерен только на одном коротком запросе Golos из шести слов. Нулевой WER на нём не является оценкой подкастов. Нормализация: нижний регистр, ё→е, пунктуация удалена, пробелы схлопнуты; числа в слова не преобразуются.

DER измерен по RTTM четырёх ru-book: шаг 10 мс, collar 0, перекрытия учитываются, speaker ID сопоставлены оптимально и взаимно однозначно. Оценены итоговые интервалы приложения после ASR, а не только сырой диаризатор. Ошибки границ, пропуски и принадлежность голосов входят в метрику. На t03–t06 DER составляет 30,1–66,9%; известное число голосов 1/2/3/3, приложение выдаёт 4/8/5/8. Это подтверждённая ошибка качества.

У подкастов нет ручной дословной и посегментной разметки. WER/DER для них не вычислялись. В t08 получилось 20 кластеров и 1477 слов; такие числа требуют ручной сверки, сами по себе точность не показывают. Вступления и музыкальные вставки также требуют проверки. Доступные записи одного подкаста не покрывают разнообразие всех разговорных шоу.

При коротком Golos текст распознан точно, но Qwen сформировал «1000000 тенге» вместо исходных «шестьдесят тысяч». Резюме нельзя использовать как достоверный источник чисел; исходная расшифровка и строгий JSON остаются отдельными.

Каждый тест запускался в свежем процессе. Утечки между тремя обработками в одном процессе, работа в фоне и при выключенном экране здесь не проверены. Память измеряется периодическими выборками PSS и может пропустить настоящий пик. Время включает задержки UI и не является изолированным временем инференса. Стадии короче периода опроса могут отсутствовать в журнале. Неудачные попытки выбора файла и раннего сбора JSON были ошибками автоматизации, архивированы и повторены; они не записаны как сбои ASR.

## Дополнительная диагностика диаризации

На ПК с sherpa-onnx 2.0.1 и теми же ONNX проверены threshold 0.5/0.65/0.8/0.95 на t03/t04. При 0.5 также получены 4/8 кластеров: проблема воспроизводится без Android UI. При 0.95 число кластеров стало 1/2, DER 6,0%/33,0%. На отложенных t05/t06 при 0.95 получены DER 16,0%/21,7%, но оба файла с тремя участниками получили только два кластера. Здесь оцениваются сырые интервалы диаризатора, а основной Android-отчёт оценивает интервалы после ASR. Это компромисс между дроблением и слиянием голосов, а не готовое исправление.

APK и production threshold 0.5 не менялись. Диагностика на ПК не считается Android-регрессией или замером скорости телефона. Результаты: [подбор](../artifacts/test-results/threshold-tuning.json), [отложенные записи](../artifacts/test-results/threshold-holdout.json).

## Следующие изменения по приоритету

1. Подготовить ручные текстовые и speaker-эталоны для нескольких независимых фрагментов подкастов: спокойный монолог, диалог, короткие ответы, музыка и перебивания. Замерить WER и DER до изменения моделей.
2. Настроить кластеризацию на отдельной выборке; сравнить более подходящую для русской речи модель speaker embeddings, короткие интервалы и объединение соседних реплик. Проверять одновременно лишние кластеры и ошибочное объединение людей.
3. Сравнить ASR по репликам с ASR по перекрывающимся окнам: слишком короткая нарезка может терять слова и контекст. Сохранять смещения исходных временных меток.
4. Проверять числа и имена резюме по расшифровке, помечать ненадёжный результат и давать повторный запуск. Изменение промпта само по себе не гарантирует отсутствие выдуманных фактов.
5. Показать ход резюме по блокам и отдельно сообщать, что расшифровка уже доступна. После выбора конфигурации собрать отдельный APK и повторить все десять файлов плюс три последовательных обработки на Redmi в авиарежиме. Не объявлять качество подтверждённым по одному короткому примеру.
