На основе этого проверенного кандидата подготовлен [предварительный релиз v1.2.3-runtime-preview.1](https://github.com/ma1sky/nuclear_hack/releases/tag/v1.2.3-runtime-preview.1). ## Итог полного приложения

| Одинаковый вход | Eres2Net: текст / весь цикл | TitaNet: текст / весь цикл | Качество |
|---|---:|---:|---|
| 3 мин, три голоса, повторённая синтетическая смесь rec_0275 | 98.05 / 191.62 с | 61.70 / 144.36 с | DER **27.84% → 30.28%**, регрессия +2.44 п.п. |
| 5 мин, естественный русский подкаст B | 157.45 / 339.11 с | 93.89 / 247.69 с | Без ручного эталона; DER/WER не заявляется |

На этих записях полный сценарий сократился на 24.7% и 27.0%, время до текста — на 37.1% и 40.4%. Это отдельные наблюдения UI, не статистическая гарантия и не скорость телефона. Время до текста включает диаризацию и ASR; полный цикл также включает обязательную локальную LLM. Основной baseline здесь — предыдущая сборка с уже реализованными пунктами 1/3, SHA 99180b3c5dcfc335d8041f14e5938d918bf92e00314d7709fefa6be55459392d.

На сложном примере осталось 4 известных ID при эталонных 3; в Eres2Net было 5 известных и неопределённые фрагменты. Уменьшение количества ID не доказало улучшения: DER на этом файле стал хуже. Быстрый профиль остаётся экспериментальным. Для сравнения и возврата есть профиль сборки Eres2Net.

## Почему выбран TitaNet

Все конфигурации используют sherpa-onnx 2.0.1, одну и ту же pyannote segmentation 3.0 INT8, mono 16 kHz и одинаковую подготовку. Количество участников автоматическое, эталон не передаётся движку.

1. На ПК порог TitaNet выбирался по четырём development-фрагментам: 0.35/0.45/0.55/0.65/0.75/0.85. Выбран cosine distance 0.75: взвешенный DER 13.75% на development без снижения числа кластеров ниже эталона. Это вспомогательная проверка количества, а не доказательство распознавания каждого человека.
2. Шесть новых русских 60-секундных фрагментов: DER 23.56% Eres2Net → 20.64% TitaNet; время 96.70 → 43.84 с на ПК. Отдельные многоголосные случаи ухудшились. Новые ID файлов не означают полностью новых голосов: пересечения голосов явно записаны в fresh-cases.json.
3. Реальный Kotlin-конвейер запущен в Android ART через app_process с теми же JNI-библиотеками из APK. Java-куча ограничена **192 МиБ**. Минутный трёхголосный тест: 14.76 с Eres2Net → 6.66 с TitaNet при одинаковом DER 13.52%.
4. Прямой перенос локального порога similarity 0.65 от Eres2Net склеивал разных участников TitaNet в длинных окнах. Этот вариант отклонён. На двух development-записях по 180 с отдельно проверены 0.85/0.90/1.01 при distance 0.75: все три дали одинаковый взвешенный DER 10.94% и три известных голоса. Детерминированно выбран первый, **0.85**.
5. После фиксации проверены три другие записи по 180 с: DER известных реплик **43.07% → 33.63%**, время диаризации **145.57 → 64.58 с**. На двух многоголосных случаях отдельно: **49.97% → 40.73%**. Это тяжёлые синтетические смеси, не естественные подкасты. На самом тяжёлом случае DER всё ещё 55.15%.

Все 180-секундные размеченные файлы созданы повторением исходных 60 секунд с сохранением эталонных speaker ID. Это стресс-тест окон, не три минуты независимого разговора. Порог подбирался на development, проверочные файлы не использовались для его выбора. Эта серия не является слепой проверкой на новых голосах: часть голосов ранее встречалась. DER рассчитан с overlap, без collar, шаг 10 мс, оптимальное сопоставление ID. Android engine DER получен до ASR-фильтрации, DER полного приложения — после неё; их нельзя напрямую смешивать.

## Число потоков

Проверены 1/2/4 отдельно для диаризации и GigaAM. В минутном Android-тесте TitaNet: 8.79 / 6.66 / 6.44 с. В диаризации оставлены **два потока**: выигрыш четвёртого небольшой.

GigaAM на одном и том же русском 20-секундном фрагменте, медиана трёх декодирований: два потока **2.618 с**, четыре **1.961 с**. Текст совпал во всех запусках. Короткий Golos: WER 0 на шести эталонных словах. Для подкастового фрагмента эталона текста нет, совпадение выходов не означает WER 0.

В приложении четыре потока ASR используются только на x86_64 при наличии минимум четырёх CPU. На ARM сохранены два до измерения на Redmi. LLM остаётся на двух потоках. Раздельные профили не меняют интерфейс и схему экспорта.

## Почему не уменьшен лимит LLM

Сравнение выполнено на ПК с тем же Qwen2.5-0.5B Q4_K_M и ChatML-промптом, llama-completion b12198. Это другая сборка llama.cpp, не замер llama.rn на Android. Четыре коротких авторских диалога дали одинаковые ответы при 160/96: модель остановилась раньше лимитов. В длинном диалоге 96 обрезало ответ посреди слова; суммы, отрицания и исполнитель не попали в результат. 160 тоже не гарантировало полноты и правильного формата. Лимит **160 сохранён**, как и обязательная локальная LLM; улучшение её содержания требует отдельной работы.

Резюме не меняет стенограмму. На пятиминутном подкасте JSON открыт примерно через 108 с, пока Qwen ещё работал; после завершения он идентичен. После отмены повторного резюме JSON также идентичен, показано завершённое сообщение об отмене. Следующее распознавание и LLM завершились успешно.

## Остальные проверки и границы

- Четыре полных случая нового APK: размеченный WAV 180 с, естественный WAV 300 с, производный AAC/M4A 60 с, Golos 4 с. Это четыре файла, а не четыре независимых источника: AAC — перекодированные первые 60 с подкаста B.
- Во всех случаях сохранение, локальное резюме, строгие поля JSON и границы целых миллисекунд прошли проверку; OOM не было. Вкладка резюме после готовности больше не сбрасывается: зафиксировано 0 повторных переходов в финальной серии.
- Наблюдавшийся максимум PSS: около 722 МиБ на трёхголосной записи и 840 МиБ на пятиминутном подкасте; после них около 163 и 181 МиБ. Это максимум выборок, не инструментированный пик и не доказательство отсутствия утечек.
- Kotlin-проверки включают часовую подготовку WAV в Java-куче 64 МиБ, потоковый ресэмплинг, отмену и сопоставление. Полный часовой инференс именно нового TitaNet APK не запускался. Для AAC проверены 60 секунд, не час.
- Полные Android-прогоны выполнены на установленном приложении в эмуляторе Android 17 x86_64, 6 vCPU, 4 ГБ, авиарежим. Это обновление установки, без удаления истории. Чистая установка нового APK и Redmi Note 11S в этой серии не проверялись.
- Точность естественных подкастов не подтверждена: ручной разметки нет. Ошибки похожих голосов, коротких ответов, перебивания и маленькой LLM остаются.

## Воспроизведение и материалы

- `tools/benchmark/runtime_options.py`: development, новые файлы, модели и потоки на ПК.
- `tools/benchmark/build-native-runtime.ps1` и `run_native_runtime.py`: реальный Kotlin/sherpa в Android без пересборки приложения под каждый параметр. Для телефона нужен ARM64 вариант библиотек и фактические замеры.
- `tools/benchmark/compare_summary_limits.py`, `summary_fixtures.json`: авторские примеры с ожидаемыми фактами.
- `tools/benchmark/run_ru_speed.py --variant <новое-имя> --apk <APK>`: полные UI-сценарии; `--manifest` позволяет отдельный набор.
- `tools/benchmark/run_summary_cancel.py`: сохранность JSON после отмены нового резюме для последней записи подкаста B.

Агрегаты, источники, параметры и хеши: `artifacts/test-results/runtime-options-2026-11-08/`. Полные тексты и скриншоты подкастов остаются в игнорируемом `recordings/`; в Git не публикуются. Предыдущая фаза: [переиспользование и ранний результат](ru-optimization-2026-11-08.md).
