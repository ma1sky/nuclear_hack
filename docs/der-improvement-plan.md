# Как снизить DER — план для текущей конфигурации

DER — ошибка диаризации, поэтому цель — снижать её. Увеличение количества speaker ID или уменьшение их количества само по себе не означает улучшения.

## Что уже выбрано

Основа — origin/main `8fc77cb`. Интерфейс, тема React Native Reusables/shadcn, история и экспорт сохранены. Приняты нормализация аудио и параметры диаризации threshold 0.8, minDurationOn 0.2 с, minDurationOff 0.3 с. Предыдущий threshold 0.55 сохранён как baseline; [исследование из 108 измерений](der-study-2026-11-07.md) подтвердило улучшение на новых данных. Автоматическое число участников сохранено.

ASR оставлен с blankPenalty 0; контекст 120 мс за пределами принадлежащего участнику интервала отключён. В коротком A/B blankPenalty 1.2 не показал выигрыша, а padding без выравнивания слов может повторно распознать соседнего говорящего. Возвращать эти эксперименты следует только с WER и проверкой принадлежности слов. Это не откат улучшенной диаризации.

На ПК новая диаризация дала DER 53.57 / 56.86 / 30.12 / 45.95% против 55.82 / 67.36 / 30.12 / 49.33% у прежней. Число кластеров всё ещё 4/6/5/7 при известных 1/2/3/3 участниках. [Полное сравнение](remote-comparison-2026-11-07.md). Это измерение сырых интервалов на ПК, а не готовая оценка нового Android APK.

В настольном A/B новой конфигурации примерно 85.9% суммарного времени ошибок — speaker confusion (95.24 с из 110.82 с). Это основание сначала проверять embeddings и кластеризацию, а не только VAD или ASR. Доля рассчитана по четырём выбранным синтетическим записям и не обобщается на все подкасты.

## Очередь экспериментов

| Приоритет | Идея | Как проверить | Риск / затраты |
|---|---|---|---|
| P0 | Разметить естественные разговоры | 6 новых фрагментов подкастов по 1–2 минуты: монолог, два и три голоса, короткие ответы, музыка, перебивания; текст и RTTM | Четыре прежних ru-book уже использовались для выбора настроек и не являются новой отложенной выборкой |
| P1 | Откалибровать кластеризацию | threshold 0.55–0.85 с шагом 0.05; minDurationOff 0.15/0.3/0.5. Сначала менять по одному параметру. minDurationOn явно 0.2, как в Android AAR | Слишком большой threshold объединяет разных людей; 0.95 уже дал 2 кластера на трёхголосых записях |
| P1 | Сравнить speaker embeddings | Текущая 3D-Speaker против совместимой ONNX-модели из каталога sherpa; WeSpeaker — кандидат для исследования, не обещание лучшего результата | Проверить вход 16 kHz, выход модели, лицензию, память, DER и скорость на Redmi; потребуется обновление хешей и комплекта моделей |
| P2 | Стабилизировать голосовые признаки | Гипотеза: строить опорные векторы по чистым неперекрытым участкам около 1.5–3 с, затем относить короткие ответы к наиболее уверенным голосам | Дополнительная логика и CPU; нельзя просто удалять короткие «да/нет» |
| P2 | Отдельно учитывать музыку и шум | Проверить VAD/музыкальный фильтр на вступлениях и шумовых участках; сравнить false alarm и missed speech | Фильтр может удалять тихую речь. Нормализация поднимает шум вместе с голосом и не заменяет VAD |
| P2 | Уточнять границы отдельно от кластеров | Сначала исправить принадлежность, затем оценивать пограничные кадры и выравнивание слов ASR | Выравнивание текста не исправляет ошибочный голосовой кластер; padding без дедупликации запрещает надёжную оценку принадлежности |
| P3 | Обрабатывать одновременную речь | Выделить overlap-интервалы в тестах и исследовать многоголосое присваивание/разделение источников | Самая затратная часть для CPU/4–6 ГБ RAM; не обещать полноценное разделение в текущем MVP |

## Правила выбора кандидата

1. Фиксировать хеши аудио и моделей, настройки, git commit и APK SHA-256. Тестовые серии хранить отдельно; исходный baseline не перезаписывать.
2. Использовать DER с collar 0 и учётом перекрытий, оптимально сопоставлять speaker ID. Сохранять отдельно missed speech, false alarm и speaker confusion. Число кластеров и ошибки коротких ответов — дополнительные диагностические показатели.
3. Улучшение принимать по новым отложенным записям, а не по файлам подбора. Проверять пропажу реальных участников и ошибочное объединение разных голосов. Не фиксировать число участников равным двум ради красивого результата.
4. При изменениях ASR дополнительно считать WER и вставки/удаления слов. LLM не исправляет speaker ID и не должна менять оцениваемую расшифровку.
5. Затем запускать новый APK на Android: короткий WAV, тишина, 2/3 голоса, M4A, длинный подкаст, отмена, три последовательных обработки, авиарежим. На Redmi измерять время и выборки PSS; результаты эмулятора не переносить на телефон.

## Практический порядок на первые 1–2 часа

- Сохранить текущий кандидат и baseline; подготовить несколько новых ручных speaker-эталонов.
- Запустить небольшой поиск threshold на прежних файлах как на наборе подбора; проверить два лучших кандидата на новых разговорах.
- Если один голос продолжает распадаться на несколько ID, сравнить вторую модель embeddings вместо дальнейшего слепого увеличения threshold.
- Только после выбора конфигурации пересобирать APK и повторять длинные прогоны. Не смешивать несколько непроверенных изменений в одном A/B.

## Основания и источники

Параметры автоматической кластеризации доступны в [примере sherpa-onnx 2.0.1](https://github.com/k2-fsa/sherpa-onnx/blob/v2.0.1/python-api-examples/offline-speaker-diarization.py). Модели для сравнения следует выбирать из [официального каталога speaker recognition](https://github.com/k2-fsa/sherpa-onnx/releases/tag/speaker-recongition-models), проверяя индивидуальные лицензии. [WeSpeaker](https://github.com/wenet-e2e/wespeaker) предоставляет инструменты исследования speaker embeddings и диаризации; совместимость конкретного экспорта и выигрыш на русском требуют отдельного теста.

Предложения P1–P3 — гипотезы для экспериментов, а не уже реализованные улучшения или гарантии DER.
